# Литература и связь с текущей работой

Эта заметка фиксирует связанные работы и отделяет результаты,
полученные в собственных экспериментах, от гипотез о механизмах.

## 1. Hugging Face Transformers: KV Cache

В основной экспериментальной части используется `QuantizedCache`
из Hugging Face Transformers с backend `hqq`.

В протестированном коде использовались параметры:

```text
backend = hqq
axis_key = 1
axis_value = 1
q_group_size = 64
residual_length = 128
```

В ablation по `q_group_size` менялся только размер группы:
16, 32, 64 и 128.

Важно: результаты работы относятся к этой конкретной реализации
`QuantizedCache`, а не к KV-cache quantization вообще.

### Поведение QuantizedCache

В Transformers 5.17.0 quantized layer хранит две части cache:

1. quantized K/V;
2. residual cache в исходной точности.

Когда residual достигает `residual_length`, его содержимое
добавляется к quantized cache и квантуется.

Перед использованием уже квантованной части cache
`QuantizedLayer.update()` вызывает dequantization для Keys и Values,
после чего возвращает attention полноточные tensors.

Это даёт возможное объяснение наблюдаемому performance trade-off:
физический storage cache уменьшается, но на decode появляется
дополнительная работа по dequantization.

В наших экспериментах это согласуется с тем, что INT4 и INT2
уменьшают память, но не ускоряют decode на NVIDIA V100.

Это объяснение относится к протестированному Transformers code path.
Оно не является утверждением о latency всех реализаций KV quantization.

## 2. KIVI

KIVI исследует tuning-free low-bit KV-cache quantization.

Важное наблюдение статьи:
распределения Keys и Values имеют разные свойства.

Авторы сообщают о channel-wise outliers в Key cache и поэтому
используют асимметричную схему:

- Keys квантуются per-channel;
- Values квантуются per-token.

Это отличается от конфигурации, использованной в текущей работе,
где для HQQ было задано:

```text
axis_key = 1
axis_value = 1
```

Поэтому результаты текущей работы нельзя трактовать
как воспроизведение KIVI.

### Связь с нашим результатом по q_group_size

На Qwen3-1.7B при INT4 наблюдалась сильная зависимость качества
от `q_group_size`:

```text
g16  -> 45/45 exact retrieval
g32  -> 37/45
g64  -> 14/45
g128 ->  4/45
```

Одно из возможных объяснений состоит в том, что при большей группе
квантизации неоднородность значений внутри группы приводит
к большему quantization error.

Наблюдения KIVI о структуре Key cache делают особенно интересной
отдельную проверку ориентации квантизации Keys.

Однако текущие эксперименты НЕ показывают напрямую,
что именно channel-wise outliers являются причиной
наблюдаемой зависимости от `q_group_size`.

Для проверки этой гипотезы нужен отдельный ablation.

### Следующий целевой эксперимент

Сохранить:

```text
axis_value = 1
```

и изменить только:

```text
axis_key: 1 -> 0
```

на Qwen3-1.7B при `q_group_size=64`.

Проверить отдельно:

```text
INT4
INT2
```

на том же наборе quality-задач.

Такой experiment является KIVI-inspired ablation,
но не полной реализацией алгоритма KIVI.

## 3. Теоретическая оценка степени сжатия HQQ

При простой групповой affine-квантизации на группу из `g` значений
хранятся:

- quantized values: `b` бит на элемент;
- scale: FP16;
- zero: FP16.

Если scale и zero занимают по 16 бит на группу,
служебные данные дают:

```text
32 / g бит на элемент
```

Тогда приблизительное эффективное число бит на элемент:

```text
b_eff = b + 32/g
```

и ожидаемая степень сжатия относительно FP16:

```text
compression ~= 16 / (b + 32/g)
```

Для конфигураций работы:

```text
INT4 g16:
16 / (4 + 32/16)
= 2.67x

INT4 g64:
16 / (4 + 32/64)
= 3.56x

INT2 g64:
16 / (2 + 32/64)
= 6.40x
```

Эти значения совпадают с измеренным физическим размером
квантованного KV Cache.

Это НЕ означает такую же степень экономии всей GPU memory,
потому что в памяти также находятся веса модели,
временные tensors и другие allocations.

---

## 4. H2O

H2O уменьшает KV Cache не за счёт уменьшения точности каждого K/V,
а за счёт выбора и сохранения части наиболее важных токенов.

Это другой класс подходов к memory reduction.

H2O не реализовывался в текущей экспериментальной работе
и используется только как related work.

---

## 5. SnapKV

SnapKV также уменьшает объём KV Cache путём отбора позиций
на основании attention-паттернов.

Как и H2O, это концептуально другой подход:
он изменяет количество хранимых состояний,
тогда как HQQ в наших основных экспериментах уменьшает
точность их представления.

SnapKV не входит в основную экспериментальную матрицу.

---

## 6. Что является собственным результатом этой работы

К литературе НЕ относятся следующие наблюдения —
они получены непосредственно в наших экспериментах:

- физическое сжатие HQQ cache и total GPU memory saving;
- снижение decode throughput на V100;
- различие robustness Qwen3 разных размеров;
- сильная зависимость INT4 quality от `q_group_size`;
- отсутствие exact retrieval у INT2 на Qwen3-1.7B
  для всех протестированных group sizes;
- short-context control на Qwen3-0.6B;
- диагностика Offloaded Cache и INT3.

Связь с KIVI используется как возможное объяснение
и как мотивация для следующего controlled experiment,
но не как доказанный механизм уже наблюдаемых результатов.

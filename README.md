# Квантизация KV Cache в малых языковых моделях: компромисс качества, памяти и скорости

Экспериментальное исследование HQQ QuantizedCache в Hugging Face Transformers
на моделях семейства Qwen3.

Работа исследует практический компромисс между тремя характеристиками:

- потреблением GPU-памяти;
- скоростью инференса;
- качеством работы модели после квантизации KV Cache.

Основные performance-эксперименты проводились на NVIDIA Tesla V100-SXM2 32 GB
на вычислительном кластере НИУ ВШЭ.

---

## Кратко о результате

В протестированных конфигурациях HQQ-квантизация существенно уменьшает
размер KV Cache, но на V100 одновременно замедляет инференс.

При этом влияние квантизации на качество сильно зависит от размера модели
и параметров самой квантизации.

На контролируемой задаче поиска восьмизначного кода в контексте
одинаковая INT4-конфигурация `q_group_size=64` дала:

| Qwen3 | Dynamic | INT4 | INT2 |
|---|---:|---:|---:|
| 0.6B | 100.0% | 14.4% | 0.0% |
| 1.7B | 100.0% | 31.1% | 0.0% |
| 4B | 100.0% | 97.8% | 0.0% |
| 8B | 95.6% | 97.8% | 2.2% |
| 14B | 100.0% | 100.0% | 26.7% |

На Qwen3-1.7B изменение только `q_group_size` при INT4 привело к:

| q_group_size | Retrieval accuracy | Total peak GPU memory saving |
|---:|---:|---:|
| 16 | 100.0% | 28.4% |
| 32 | 82.2% | 31.2% |
| 64 | 31.1% | 32.6% |
| 128 | 8.9% | 33.3% |

Таким образом, в этой конфигурации дополнительная экономия общей
GPU-памяти при увеличении `q_group_size` оказалась относительно небольшой,
тогда как качество retrieval снижалось значительно сильнее.

---

## Исследовательские вопросы

**RQ1.** Насколько HQQ-квантизация KV Cache уменьшает реальное
потребление GPU-памяти и как влияет на скорость инференса?

**RQ2.** Как устойчивость к одной и той же конфигурации квантизации
меняется с размером модели Qwen3?

**RQ3.** Насколько `q_group_size` влияет на компромисс между качеством
и экономией памяти?

**RQ4.** Является ли деградация качества малых моделей исключительно
следствием длинного контекста?

## Мотивация

При авторегрессионной генерации Transformer-модель сохраняет
key/value состояния предыдущих токенов в KV Cache.

Это позволяет не пересчитывать состояния всех предыдущих токенов
на каждом шаге генерации, но размер KV Cache растёт вместе
с длиной контекста.

На длинных последовательностях KV Cache может занимать значительную
часть GPU-памяти. Один из способов уменьшить это потребление —
хранить key/value состояния с более низкой точностью.

Однако уменьшение памяти само по себе не гарантирует,
что метод будет практически полезным:

- квантизация может добавить вычислительный overhead;
- качество генерации может ухудшиться;
- реальная экономия всей GPU-памяти меньше,
  чем степень сжатия самого KV Cache.

Поэтому цель работы — экспериментально измерить эти компромиссы
для доступной из коробки реализации HQQ QuantizedCache
в Hugging Face Transformers.

## Экспериментальная постановка

### Модели и оборудование

В экспериментах использовались модели семейства Qwen3:

- Qwen3-0.6B;
- Qwen3-1.7B;
- Qwen3-4B;
- Qwen3-8B;
- Qwen3-14B.

Основные performance-эксперименты для моделей 0.6B–8B проводились
на одной NVIDIA Tesla V100-SXM2 с 32 GB GPU-памяти.

Qwen3-14B не помещалась на одну V100 в используемой точности,
поэтому для неё проводилась quality-проверка на двух V100.
Её latency напрямую не сравнивается с результатами меньших моделей.

Основной программный стек:

- Python 3.11;
- PyTorch 2.14.0;
- CUDA 12.6;
- Transformers 5.17.0;
- HQQ 0.2.8.post1.

### Сравниваемые варианты KV Cache

В основной части работы сравнивались:

- `DynamicCache` — baseline без квантизации KV Cache;
- HQQ INT8;
- HQQ INT4;
- HQQ INT2.

Для основного сравнения моделей использовались параметры:

```text
q_group_size = 64
residual_length = 128
```

Дополнительно на Qwen3-1.7B исследовалось влияние `q_group_size`:

```text
16
32
64
128
```

для INT4 и INT2.

`q_group_size` определяет, сколько значений квантуются совместно
с одним набором параметров квантования.

Меньший размер группы требует больше служебных данных,
но позволяет использовать параметры квантования для меньших участков
исходных данных.

### Performance-эксперименты

В performance-экспериментах отдельно измерялись:

- время prefill;
- скорость decode в tokens/s;
- end-to-end время;
- максимальное использование GPU-памяти;
- физический размер KV Cache.

`Prefill` — этап, на котором модель обрабатывает весь входной контекст.

`Decode` — последующая авторегрессионная генерация новых токенов.
На этом этапе KV Cache позволяет использовать уже вычисленные key/value
состояния предыдущих токенов вместо их полного пересчёта.

Основные длины контекста для сравнения моделей:

```text
8192
16384
32768
40895
```

Каждая performance-конфигурация запускалась несколько раз после warm-up.
Итоговые значения усреднялись по успешным повторам.

Для финальной Qwen3-1.7B ablation каждая конфигурация запускалась
по три раза на каждой длине контекста.

### Оценка качества

Для оценки качества использовалась контролируемая синтетическая
retrieval-задача.

В длинный текст помещался случайный восьмизначный код.
После чтения контекста модель должна была восстановить этот код.

Положение кода в контексте менялось:

```text
10%
50%
90%
```

от длины последовательности.

Использовались разные случайные seeds, чтобы результат не зависел
от одного конкретного текста или одного кода.

Основная метрика:

- `retrieval exact-match` — доля случаев, в которых восьмизначный код
  был восстановлен полностью правильно.

Дополнительно измерялись:

- teacher-forced top-1 accuracy для последующих токенов ответа;
- teacher-forced negative log-likelihood (`NLL`).

Эти дополнительные метрики помогают отличить полный провал retrieval
от ситуации, когда модель всё ещё часто предсказывает правильные токены,
но допускает одну или несколько ошибок в полном восьмизначном ответе.

Для сравнения качества моделей разных размеров использовались контексты:

```text
8192
16384
32768
```

На Qwen3-0.6B также был проведён отдельный short-context control
на длинах:

```text
2048
4096
```

Его цель — проверить, можно ли объяснить сильную деградацию качества
маленькой модели исключительно большой длиной KV Cache.

### Воспроизводимость

Все тяжёлые эксперименты запускались через Slurm на GPU-узлах кластера.

Для каждого запуска сохранялись:

- модель и конфигурация cache;
- длина контекста;
- версии библиотек;
- GPU;
- измерения памяти и времени;
- output hash;
- информация об ошибках.

Сырые результаты находятся в `results/raw/`.

Финальные агрегированные таблицы строятся автоматически скриптом:

```text
src/analyze_final.py
```

и сохраняются в:

```text
results/summary/final/
```

Финальные графики сохраняются в:

```text
plots/final/
```

## Результаты

### 1. Базовая проверка измерений KV Cache

Перед исследованием квантизации была проверена базовая зависимость
размера KV Cache от длины контекста.

Для Qwen3-0.6B с `DynamicCache` измеренный физический размер KV Cache
практически совпал с теоретической оценкой:

| Context | Dynamic KV Cache |
|---:|---:|
| 8192 | 0.875 GiB |
| 16384 | 1.750 GiB |
| 24576 | 2.625 GiB |
| 32768 | 3.500 GiB |
| 40895 | 4.368 GiB |

Таким образом, размер KV Cache в этих экспериментах рос практически
линейно с длиной контекста.

Этот результат использовался как sanity check:
он показывает, что измеряемый размер cache соответствует ожидаемой
архитектуре модели, а не является случайным артефактом measurement pipeline.

### 2. Квантизация экономит память, но замедляет инференс

Для основного сравнения использовались HQQ INT4 и INT2
с `q_group_size=64`.

На Qwen3-1.7B при контексте 40895 токенов:

| Cache | KV Cache | Total peak GPU memory | Decode speed |
|---|---:|---:|---:|
| Dynamic | 4.368 GiB | 9.640 GiB | 9.81 tok/s |
| INT4 | 1.229 GiB | 6.497 GiB | 6.33 tok/s |
| INT2 | 0.683 GiB | 5.950 GiB | 6.24 tok/s |

Для INT4 это соответствует примерно:

- `3.56x` сжатию физического KV Cache;
- `32.6%` уменьшению total peak GPU memory;
- `35.5%` снижению decode throughput.

Для INT2:

- `6.4x` сжатию физического KV Cache;
- `38.3%` уменьшению total peak GPU memory;
- `36.4%` снижению decode throughput.

Это показывает важное различие между двумя величинами:

> сильное сжатие самого KV Cache не означает такое же уменьшение
> общего потребления GPU-памяти.

В памяти также находятся веса модели и другие данные,
поэтому выигрыш по total VRAM всегда меньше степени сжатия cache.

Кроме того, в протестированной реализации HQQ на V100
квантизация не ускорила inference.

В данном experimental setup её практический выигрыш состоит
в уменьшении потребления памяти, а ценой является дополнительная latency.

![GPU memory vs context](plots/final/memory_vs_context_qwen17.png)

На графике видно, что преимущество квантизированного cache по памяти
становится всё заметнее с увеличением длины контекста.

Одновременно decode throughput у quantized cache остаётся ниже Dynamic:

![Decode speed vs context](plots/final/decode_speed_vs_context_qwen17.png)

Поэтому memory saving и inference speed необходимо рассматривать
как разные стороны одного trade-off.

### 3. Устойчивость к INT4 зависит от размера модели

Далее проверялось, одинаково ли одна и та же конфигурация HQQ
влияет на Qwen3 разных размеров.

Во всех случаях использовался `q_group_size=64`.

Результат по retrieval exact-match:

| Qwen3 | Dynamic | INT4 | INT2 |
|---|---:|---:|---:|
| 0.6B | 100.0% | 14.4% | 0.0% |
| 1.7B | 100.0% | 31.1% | 0.0% |
| 4B | 100.0% | 97.8% | 0.0% |
| 8B | 95.6% | 97.8% | 2.2% |
| 14B | 100.0% | 100.0% | 26.7% |

![Retrieval quality vs model size](plots/final/model_size_quality.png)

На контролируемой retrieval-задаче одна и та же INT4-конфигурация
оказалась очень разрушительной для Qwen3-0.6B и Qwen3-1.7B,
но почти не ухудшала результат Qwen3-4B, Qwen3-8B и Qwen3-14B.

Это не означает существование универсального порога около 4B параметров.
Эксперимент проверяет только конкретные модели Qwen3,
конкретную реализацию HQQ и конкретную retrieval-задачу.

Корректный вывод более узкий:

> в протестированном benchmark более крупные модели Qwen3
> оказались существенно устойчивее к одной и той же
> HQQ INT4 KV-cache quantization.

Разница `95.6%` для Dynamic и `97.8%` для INT4 на Qwen3-8B
не интерпретируется как улучшение качества от квантизации:
при таком количестве задач небольшая разница может быть обычной
выборочной вариацией.

INT2 оказался значительно более агрессивным.
Для моделей до 4B exact retrieval был равен нулю,
а даже Qwen3-14B восстановила код полностью правильно
только в 26.7% случаев.

Это не означает, что 2-bit KV-cache quantization в целом не работает.
Результат относится только к протестированной HQQ-конфигурации.

### 4. `q_group_size` сильно влияет на качество INT4

Самый заметный эффект был обнаружен в отдельной ablation
на Qwen3-1.7B.

При одинаковом INT4 bit-width изменялся только `q_group_size`.

Retrieval accuracy:

| q_group_size | Accuracy |
|---:|---:|
| 16 | 100.0% |
| 32 | 82.2% |
| 64 | 31.1% |
| 128 | 8.9% |

![INT4 group-size quality](plots/final/int4_group_size_quality.png)

При этом дополнительный выигрыш по общей GPU-памяти был значительно
меньше изменения качества:

| Configuration | Retrieval | KV compression | Total peak saving |
|---|---:|---:|---:|
| Dynamic | 100.0% | 1.00x | 0.0% |
| INT8 g64 | 100.0% | 1.88x | 21.3% |
| INT4 g16 | 100.0% | 2.67x | 28.4% |
| INT4 g32 | 82.2% | 3.20x | 31.2% |
| INT4 g64 | 31.1% | 3.56x | 32.6% |
| INT4 g128 | 8.9% | 3.77x | 33.3% |

Например, переход от `INT4 g16` к `INT4 g64` увеличил
экономию total peak GPU memory примерно с `28.4%` до `32.6%`.

То есть дополнительный выигрыш составил около 4 процентных пунктов.

Однако retrieval accuracy одновременно снизилась:

```text
100.0% -> 31.1%
```

Decode throughput при разных INT4 group sizes почти не менялся
и оставался около `6.34 tok/s`.

Следовательно, в этом эксперименте изменение `q_group_size`
в первую очередь влияло на качество и memory footprint,
а не на скорость decode.

![Quality-memory trade-off](plots/final/quality_memory_tradeoff.png)

Для данной модели и данной контролируемой retrieval-задачи
`INT4 g16` оказался особенно интересной рабочей конфигурацией:
он сохранил 100% measured retrieval accuracy,
одновременно уменьшив total peak GPU memory примерно на 28%.

Это не означает, что `g16` является оптимальным параметром
для других моделей или задач.

Для INT2 ситуация была другой:

| q_group_size | Retrieval accuracy |
|---:|---:|
| 16 | 0.0% |
| 32 | 0.0% |
| 64 | 0.0% |
| 128 | 0.0% |

То есть уменьшение размера группы само по себе
не восстановило exact retrieval для INT2 на Qwen3-1.7B.

### 5. Деградация малой модели наблюдается и на коротком контексте

После long-context экспериментов оставалось альтернативное объяснение:

> возможно, Qwen3-0.6B плохо переносит INT4 только потому,
> что квантуется очень длинный KV Cache.

Для проверки был проведён отдельный control experiment
на контекстах 2048 и 4096 токенов.

Результат:

| Cache | 2048 | 4096 |
|---|---:|---:|
| Dynamic | 100.0% | 100.0% |
| INT4 g64 | 6.7% | 0.0% |
| INT2 g64 | 0.0% | 0.0% |

Dynamic baseline по-прежнему решал все задачи,
но INT4 и INT2 сильно ухудшали результат уже на коротком контексте.

Следовательно, наблюдаемую деградацию Qwen3-0.6B
нельзя объяснить исключительно большой длиной KV Cache.

При этом эксперимент не показывает простой монотонной зависимости
качества от длины контекста:
его задача — только проверить, присутствует ли проблема уже
при небольших context lengths.

## Дополнительные эксперименты

### DynamicCache и StaticCache

До основной серии с HQQ была проведена базовая systems-проверка
`DynamicCache` и `StaticCache` на Qwen3-0.6B.

Без compilation `StaticCache` не дал выигрыша по памяти
и был медленнее `DynamicCache` на длинных контекстах.

Дополнительно был проверен `StaticCache` вместе с `torch.compile`.

В steady-state режиме compiled Static был быстрее Dynamic
на коротких и средних контекстах, но преимущество исчезало
между протестированными 8K и 12K.

На более длинных контекстах Dynamic снова оказался быстрее.

При этом cold compilation имела большой первоначальный overhead,
поэтому этот результат рассматривается как отдельное systems-наблюдение,
а не как центральная часть работы.

### Offloaded Cache

Для Offloaded Cache была обнаружена проблема воспроизводимости:
на более длинных контекстах результаты могли расходиться
с обычным DynamicCache.

Дополнительные проверки показали зависимость эффекта
от backend и synchronization.

При `CUDA_LAUNCH_BLOCKING=1` расхождение сдвигалось или исчезало
на части протестированных конфигураций.

Этого недостаточно, чтобы утверждать наличие конкретного бага
в Transformers, поэтому Offloaded Cache не использовался
для основных performance-выводов.

Подробности сохранены в `notes/offloaded_correctness.md`.

### INT3

Также была проверена возможность HQQ INT3.

В использованной версии HQQ путь деквантизации INT3 завершался ошибкой
для протестированных group sizes.

Поскольку проблема возникала ниже уровня основной интеграции Transformers,
INT3 не использовался в основной экспериментальной матрице.

Этот результат трактуется как ограничение протестированного software stack,
а не как утверждение о невозможности INT3-квантизации вообще.

## Ограничения

У работы есть несколько важных ограничений.

### Одна семья моделей

Эксперименты проводились только на Qwen3.

Поэтому наблюдаемую зависимость устойчивости от размера модели
нельзя автоматически переносить на другие model families.

### Одна основная quality-задача

Качество измерялось на контролируемой synthetic passkey retrieval-задаче.

Она удобна тем, что:

- имеет однозначный правильный ответ;
- позволяет контролировать длину контекста;
- позволяет менять положение искомой информации;
- даёт простой exact-match.

Но она не измеряет общее качество модели
на reasoning, summarization, dialogue или других long-context задачах.

Поэтому результаты quality-экспериментов следует интерпретировать
именно как устойчивость на controlled retrieval benchmark.

### Конкретная реализация квантизации

Исследовался HQQ QuantizedCache в Hugging Face Transformers.

Результаты нельзя интерпретировать как свойства
KV-cache quantization вообще.

Другие методы могут использовать другую схему квантизации,
специализированные low-bit kernels или иные способы обработки
Keys и Values.

### Аппаратная платформа

Основные performance-результаты получены на NVIDIA V100.

На более новых GPU абсолютные значения latency и throughput
могут отличаться.

Особенно это важно для quantized inference,
где специализированные kernels могут существенно менять performance.

### Qwen3-14B

Quality для Qwen3-14B измерялась на двух V100,
тогда как performance для 0.6B–8B — на одной V100.

Поэтому 14B включена только в quality scaling
и не используется для прямого сравнения latency.

---

## Основные выводы

По результатам экспериментов можно сделать следующие выводы.

1. **HQQ-квантизация действительно существенно уменьшает размер KV Cache.**

   При `q_group_size=64` INT4 сжимал физический KV Cache примерно в `3.56x`,
   а INT2 — примерно в `6.4x`.

2. **Сжатие KV Cache не равно такому же уменьшению всей GPU-памяти.**

   Например, на Qwen3-1.7B при ~41K INT4 уменьшал KV Cache
   с `4.368 GiB` до `1.229 GiB`, но total peak GPU memory —
   с `9.640 GiB` до `6.497 GiB`.

3. **В протестированной реализации экономия памяти сопровождалась
   замедлением inference.**

   На Qwen3-1.7B при ~41K decode throughput снизился
   примерно с `9.81 tok/s` до `6.33 tok/s` для INT4.

4. **Устойчивость к одной и той же INT4-конфигурации заметно менялась
   с размером Qwen3.**

   На controlled retrieval benchmark INT4 g64 дала
   `14.4%` exact retrieval для 0.6B,
   `31.1%` для 1.7B
   и около `98–100%` для протестированных 4B–14B моделей.

5. **`q_group_size` оказался одним из важнейших параметров качества.**

   На Qwen3-1.7B INT4 g16 сохранил `100%` retrieval,
   тогда как g64 дал `31.1%`, а g128 — `8.9%`.

   Дополнительный выигрыш по total peak GPU memory
   при этом был сравнительно небольшим.

6. **INT2 оказался слишком агрессивным для Qwen3-1.7B
   на данной задаче.**

   Ни один из протестированных group sizes не восстановил
   exact retrieval.

7. **Проблема малой модели не является только long-context эффектом.**

   На Qwen3-0.6B сильная деградация INT4 и INT2
   наблюдалась уже на контекстах 2K и 4K.

Главный практический вывод работы:

> при использовании KV-cache quantization недостаточно выбирать
> только bit-width.
>
> Параметры квантизации, размер модели и фактический
> quality-memory-latency trade-off необходимо проверять совместно.
